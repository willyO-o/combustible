# V1

## colecciones(): vehiculos se deriva de datos, no del rol
ParametrosController::colecciones() NO asume que el usuario sea conductor. persona->conductor puede ser null (jefe de área) y una persona puede tener ambos roles. El array `vehiculos` unifica con unique('id'): conductor->asignacionesActivas + los vehiculosActivos de persona->encargadoAreas() (áreas que administra como jefe de área). `areas` (para actividades sugeridas) = conductor->areas() + encargadoAreas()->pluck('id'). Si no es ninguno, vehiculos llega vacío (ya no hay 500). Cubierto por ParametrosControllerTest.

## API V1 órdenes de trabajo: ejecución completa del técnico
Api\V1\OrdenTrabajoController expone: index/show, iniciar (PATCH .../iniciar → PENDIENTE→EN_EJECUCION + fecha_ejecucion), storeDetalle (POST .../detalles), updateDetalle (PUT/PATCH .../detalles/{detalle}, reemplazo completo — misma request que store) y destroyDetalle (DELETE .../detalles/{detalle}), culminar (POST .../culminar → EN_EJECUCION→CULMINADO, exige ≥1 detalle + lecturas finales). Param de ruta `orden`. La emisión de la orden (Paso 2) y VERIFICADO/CANCELADO siguen siendo sólo web.
- Requests compartidos con web: DetalleMantenimientoRequest y EjecucionOrdenTrabajoRequest — ambos ya autorizan tecnico-mantenimiento vía $this->route('orden')->id_usuario_ejecuta; a ambos se les añadió failedValidation() guardado por expectsJson() para el envelope JSON de la API.
- iniciar/detalle: sólo con estado PENDIENTE/EN_EJECUCION; culminar: sólo EN_EJECUCION. Fuera de estado → 422 (no excepción).
- GET /parametros/colecciones → `ordenes_trabajo` = {estados_orden (array simple), estados (value/label/descripcion), acciones_tecnico (accion/metodo/ruta/desde/estado_resultante — incluye `editar_detalle`), tipos_mantenimiento (catálogo activo), repuestos (activos)}.
- Todo documentado en openapi.yaml, tag "Órdenes de Trabajo". Usuarios de prueba tecnico1@gmail.com / tecnico2@gmail.com (tecnico123) — ya existían en UserSeeder, se agregaron a la tabla de la doc.

## API V1: endpoints de descarga de PDF por registro
Patrón para exponer en la API el PDF de un registro (mismo que ValeController::pdf y SolicitudMantenimientoController::pdf):
- Ruta `GET {recurso}/{modelo}/pdf` declarada ANTES del Route::resource (para no chocar con show), nombre `api.v1.{recurso}.pdf`.
- Método `pdf(Request $request, Modelo $m): Response`. Chequeo de rol inline: si `hasRole('conductor')` y el registro no es suyo (`$m->id_conductor !== $request->user()->id_persona`) → `abort(403, '...')`.
- `->load([...relaciones...])`, luego `(new Reportes)->generar*($m, 'S')`, y `response($contenido, 200, ['Content-Type' => 'application/pdf', 'Content-Disposition' => 'attachment; filename="..."'])`. El `/` del nro se reemplaza por `-` en el filename.
Endpoints actuales: vales, solicitudes-mantenimiento, operacion-diaria (reporte, tiposMantenimiento=null → lo resuelve Reportes), cargas (comprobante de egreso, generarComprobanteEgreso). Todo documentado en openapi.yaml + CHANGELOG-openapi.md. Tests: *PdfControllerTest.php en tests/Feature/Api/V1.

## API V1: chequeo de permisos (no roles) bajo auth:api requiere guard explícito
Bajo `auth:api`, el middleware Authenticate de Laravel 11 llama `Auth::shouldUse('api')`, así que `config('auth.defaults.guard')` pasa a ser `api`. Spatie resuelve el guard por defecto desde ahí → `api`. Como todos los roles/permisos del proyecto tienen guard `web`:
- `hasRole('x')` / `hasAnyRole([...])` SIN pasar guard funcionan igual (Spatie sólo compara nombres en `$this->roles`). Es el patrón usado en toda la API V1.
- `->can('perm')` y `hasPermissionTo('perm')` SIN guard fallan/devuelven false (buscan la permission en guard `api`, que no existe). `->can()` además NO recibe el bypass de super-admin porque el `Gate::before` de AppServiceProvider sólo aplica a Gate, y aquí el fallo es previo.
Solución al chequear un permiso real: `$user->hasRole('super-admin') || $user->hasPermissionTo('perm', 'web')` (guard explícito). Ejemplo: Api\V1\CargaMaterialController::pagar() con `control-cargas.marcar-pagado`.
