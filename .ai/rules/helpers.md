# Helpers

## Evidencia fotográfica en mantenimiento_operacion_diaria (convertida a webp)
A pedido del usuario (2026-09), cada control de mantenimiento de operación diaria admite una foto de evidencia opcional: `mantenimiento_operacion_diaria.evidencia` (string 255 nullable, ruta relativa disco 'public', igual convención que vehiculo.fotografia).

**Conversión a webp**: nuevo helper global `convertirImagenAWebp(UploadedFile, $directorio, $disco='public', $calidad=80, $ladoMaximoPx=1920)` en app/Helpers/helpers.php (autoloaded vía composer "files", sin librerías nuevas — usa GD, ya viene con PHP). Corrige orientación EXIF de fotos de celular (helper `corregirOrientacionExif()`, mismo archivo), redimensiona si excede 1920px del lado mayor, y devuelve la ruta relativa con el mismo contrato que `UploadedFile::store()`. Si GD no puede leer el archivo, cae a guardarlo tal cual (no rompe el flujo). Reusar este helper para cualquier otra foto que se quiera aligerar (no se retrofitteó a fotografia/foto existentes — sólo se usa para evidencia, a menos que el usuario pida extenderlo).

**Sincronización (SincronizarMantenimientosOperacionAction)**: sigue haciendo detach()+attach() completo en cada guardado (create/update comparten la Action), pero ahora: (1) lee las evidencias YA guardadas antes del detach() (única forma de conservarlas — el cliente nunca reenvía la ruta, sólo un File cuando cambia); (2) si llega `evidencia` (UploadedFile) para un id_tipo_mantenimiento, reemplaza (borra la vieja del disco, convierte+guarda la nueva); (3) si llega `eliminar_evidencia:true` sin archivo nuevo, borra sin reemplazar; (4) si no llega ninguno de los dos, conserva la existente; (5) un control se considera "registrado" (se attach()ea) si tiene valor, realizado O evidencia — antes sólo valor/realizado; (6) al final, borra del disco las evidencias de tipos que ya no quedaron adjuntos (se destildaron o no vinieron en el envío), evitando huérfanos. `destroy()` de OperacionDiaria (web Y API, mismo método privado `eliminarEvidenciasMantenimiento()` duplicado en ambos controllers) borra todas las evidencias antes de eliminar la operación.

**Validación** (OperacionStoreRequest, compartida web+API): `mantenimientos.*.evidencia` nullable|image|mimes:jpg,jpeg,png,webp,avif|max:8192; `mantenimientos.*.eliminar_evidencia` nullable|boolean.

**Frontend** (Operacion/Create.vue): cada fila de `form.mantenimientos` tiene `evidencia` (File a subir o null), `evidencia_actual` (ruta ya guardada, sólo para preview — NUNCA se reenvía tal cual) y `eliminar_evidencia`. `evidenciaPreview` (ref, keyed por id_tipo_mantenimiento) maneja la miniatura, con FileReader al elegir archivo nuevo (mismo patrón que la foto de Vehiculo). El filtro que decide qué filas mandar al backend ahora también incluye filas con evidencia/evidencia_actual aunque no tengan valor/realizado — si no, el backend nunca las ve y borra su evidencia por "huérfana". `.post(routeName, { forceFormData: true })` — antes no hacía falta forceFormData (sin archivos). CSS nuevo en resources/css/my-styles.css bajo `.mant-evidencia-*` (sigue el patrón de tokens de tema ya usado por `.mant-*`). Show.vue sólo muestra una miniatura clicable (link a `/storage/...`), sin edición.

**API/OpenAPI**: mismo OperacionStoreRequest → automático en Api/V1/OperacionDiariaController (store/update comparten Request y Action). openapi.yaml bump 1.5.0→1.6.0 (info.version + api_version en 2 lugares + ParametrosController::index()): `MantenimientoOperacionInput.evidencia/eliminar_evidencia`, `MantenimientoOperacionRegistrado.pivot.evidencia`, sección nueva "Envío con evidencia fotográfica" + alternativa `multipart/form-data` en requestBody de POST y PUT /operacion-diaria (mismo patrón que `respaldos` en POST /cargas — notación de corchetes anidados). CHANGELOG-openapi.md con entrada 1.6.0.

Tests: OperacionDiariaControllerTest (web, 5 tests: guarda+convierte a webp, conserva sin archivo nuevo, reemplaza y borra la anterior, elimina con eliminar_evidencia, destroy borra archivos) y Api/V1/OperacionDiariaControllerTest (2 tests, mismo patrón pero con ->post() en vez de ->postJson() para el multipart — ver comentario en el test). ## Evidencia de mantenimiento_operacion_diaria es OBLIGATORIA (no opcional)
ACTUALIZACIÓN sobre [[Evidencia fotográfica en mantenimiento_operacion_diaria (convertida a webp)]]: a pedido del usuario, la evidencia dejó de ser opcional. Regla final: `mantenimientos.*.evidencia` es OBLIGATORIA para todo control que se registre con `valor` (tipo cantidad) o `realizado = SI` (tipo booleano). Marcar `realizado = NO` NO exige evidencia — no hay nada que fotografiar de un control que no se hizo. Confirmado explícitamente por el usuario (no aplica a "NO", sí aplica cuando hay valor cargado).

**Cómo se valida** (OperacionStoreRequest): NO se puede resolver como regla normal en `rules()` — una regla de archivo (`image`, `mimes`, o un closure común, no marcado `ImplicitRule`) simplemente no se ejecuta cuando el campo llega ausente, que es exactamente el caso a detectar (sin archivo nuevo). Se resuelve con `withValidator()` + `$validator->after()` (mismo patrón ya usado en `EncargadoAreaRequest`): recorre `mantenimientos` a mano, y si el control requiere evidencia (`valor` no vacío o `realizado === 'SI'`) y no llega `hasFile("mantenimientos.$idx.evidencia")`, revisa si YA existe una evidencia guardada en BD (edición, `$this->route('operacionDiaria')`, tabla `mantenimiento_operacion_diaria` directamente — no vale para creación) y sólo entonces la deja pasar; si no, agrega error a `mantenimientos.$idx.evidencia`.

**Consecuencia sobre `eliminar_evidencia`**: sólo tiene efecto real si el control ADEMÁS deja de traer `valor`/`realizado=SI` en el mismo envío (para que deje de "requerir" evidencia). Pedir `eliminar_evidencia:true` mientras el control sigue con `realizado:'SI'` falla con 422 en `mantenimientos.$idx.evidencia` — no se puede marcar un control como hecho sin evidencia quitándosela aparte. La Action (`SincronizarMantenimientosOperacionAction`) no cambió su lógica de por sí; el bloqueo ocurre en la validación, antes de que la Action se ejecute.

**Frontend** (Operacion/Create.vue): `evidenciaRequerida(m)` (helper nuevo) replica el mismo criterio en el cliente sólo para dar una pista visual (borde rojo en el botón de cámara vía clase `.mant-evidencia-btn--requerida` en my-styles.css) — NO bloquea el submit del lado cliente, la autoridad real es el servidor (mismo criterio que el resto de reglas condicionales de esta request, ej. kilometraje_inicio/horometro_inicio, que tampoco se bloquean en JS).

Todos los tests preexistentes de mantenimientos (ambos archivos, web y API) que enviaban `valor`/`realizado:'SI'` sin evidencia se actualizaron para incluir `UploadedFile::fake()->image(...)` — si no, el `store`/`update` fallaba con 422 y `OperacionDiaria::firstOrFail()` reventaba. Nuevos tests: exige evidencia con valor, exige con booleano SI, NO exige con booleano NO, no permite eliminar evidencia de un control activo (SI), eliminar_evidencia sí funciona si además se destilda el control — en OperacionDiariaControllerTest (web) y su espejo en Api/V1/OperacionDiariaControllerTest.

openapi.yaml actualizado en el mismo bloque 1.6.0 (no se bumpeó a 1.7.0 — es refinamiento de la misma iteración, aún no publicada): `MantenimientoOperacionInput.evidencia`/`.eliminar_evidencia` documentan la obligatoriedad condicional, sección "Envío con evidencia fotográfica" con ejemplo de un control NO que no la necesita, bullets de POST/PUT actualizados.
